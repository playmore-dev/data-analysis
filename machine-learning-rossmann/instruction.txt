### Stage 2 — Feature Engineering

Prepare a feature matrix suitable for supervised regression.

#### 2.1. Date-Based Features

Where a valid date variable exists, extract relevant features such as:

- Year, month, day of month, and day of week.
- Week of year.
- Weekend indicators, where relevant.
- Seasonal or calendar-period indicators, where justified.

Consider cyclical representations of calendar variables when useful for the selected model.

#### 2.2. Store and Business Features

Use relevant available variables, such as:

- Store type and assortment.
- Promotion indicators.
- Holiday or school-holiday indicators.
- Competition distance and competition-opening information.
- Other documented store characteristics.

Encode categorical variables and handle missing values appropriately. Use preprocessing pipelines where beneficial.

#### 2.3. Historical Sales Features

Where sufficient historical observations are available, consider features such as:

- Previous-day sales.
- Sales on the same weekday in previous weeks.
- Rolling mean and rolling variability over selected historical windows.

Construct these features separately for each store and in chronological order.

Every historical feature must use only information available before the date being predicted. Ensure that rolling calculations, shifting operations, and validation boundaries do not introduce future information.

#### 2.4. Feature Availability and Leakage Prevention

Define the prediction scenario explicitly: predicting sales for a future store-day using information available at the time of prediction.

Exclude variables that would not be available at that time. For example, actual customer counts for the day being predicted must not be used to forecast that day's sales in advance.

Also avoid using:

- Future sales observations.
- Target-derived information unavailable at prediction time.
- Validation-period outcomes during training or feature construction.
- Transformations fitted using validation data.

Document the final target variable, predictor features, and assumptions about information availability.

#### 3.1. Define the Modeling Task

- **Target:** Daily `Sales`, if inspection confirms that this variable exists and represents the intended outcome.

#### 3.3. Build Regression Models

Train and compare the following models, where supported by the available data:

#### 3.4. Train/Validation Strategy

Use a chronological train/validation split rather than randomly shuffling observations across time.

- Train on earlier dates.
- Validate on a later, unseen period.
- Apply the same validation dates to all models.
- Ensure that lagged and rolling features use only historical information.
- Document the split dates and the number of observations in each partition.

If useful, perform additional time-based validation to assess whether model performance is stable across different periods.

When using multiple stores, preserve the intended forecasting scenario. Explain whether the model is evaluated on future dates for known stores or on stores not represented in training, as these are different generalization tasks.

#### 3.5. Evaluation Metrics

Evaluate all models on the same validation observations using the following metrics.

**Mean Absolute Error (MAE)**

Measures the average absolute difference between actual and predicted sales. It is expressed in the same units as sales and is relatively easy to interpret.

**Root Mean Squared Error (RMSE)**

Measures the square root of the average squared prediction error. It penalizes large errors more heavily than MAE.

**Coefficient of Determination (\(R^2\))**

Measures predictive performance relative to predicting the observed target mean. Interpret the result in the context of the validation data.

Compare all models in a single results table.

- Lower MAE is generally preferable.
- Lower RMSE is generally preferable.
- Higher \(R^2\) is generally preferable.

Explain what the metrics mean in practical terms. Do not assume that a complex model performs better simply because it is more advanced.

If sales values are heavily concentrated in certain ranges, consider reporting additional diagnostic measures or segment-level errors to provide a more complete assessment.

- Identify the strongest candidate based on validation results.
- Tune selected hyperparameters if beneficial.
- Compare tuned and untuned performance.
- Assess whether improvements are meaningful.
- Consider interpretability, computational cost, and complexity alongside predictive accuracy.

Use validation results for model selection. If a separate final test period is available and justified, reserve it for an independent final assessment.

Do not claim that a model generalizes well solely because it performs well on training data.

#### 3.7. Model Interpretation and Error Analysis

- Examine absolute prediction errors.
- Compare performance across stores, weekdays, months, and promotion conditions where appropriate.
- Investigate systematic overprediction or underprediction.
- Examine feature importance using a suitable method.

Explain what the analysis reveals about model strengths and weaknesses.

Feature importance and predictive associations must not be presented as proof of causal relationships.
